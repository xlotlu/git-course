# 2.2. Recording Changes to the Repository  

Git's power lies in its ability to track and record changes to files efficiently. This chapter explains the key concepts of Git’s architecture, how to manage file changes, and how to create commits that capture the state of your project.

---

## Tracked vs Untracked Files

Each file in your working directory can be in one of two states: tracked or untracked. Tracked files are files that were in the last snapshot, as well as any newly staged files; they can be unmodified, modified, or staged. In short, tracked files are files that Git knows about.

Untracked files are everything else — any files in your working directory that were not in your last snapshot and are not in your staging area. When you first clone a repository, all of your files will be tracked and unmodified because Git just checked them out and you haven’t edited anything.

As you edit files, Git sees them as modified, because you’ve changed them since your last commit. As you work, you selectively stage these modified files and then commit all those staged changes, and the cycle repeats.

---

## Understanding the Working Directory, Staging Area, and Git Directory

To effectively use Git, it’s crucial to understand its three main states: modified, staged, and committed. These states determine how your files transition through the Git workflow.

### Working Directory

The working directory is your local environment where you modify and create files. This is where your active development takes place. Tracked files that have been changed are **modified**.

### Staging Area

The staging area is like a clipboard where you prepare changes for your next commit. It allows you to carefully select which changes to include in the commit. Modified files added to the staging area are **staged**.

### Git Directory

The Git directory is the database where Git stores all the information about your project, including the commit history and your current working state. Staged files added to the git directory are **committed**.

### The Basic Workflow

1. **Modify Files**: Edit files in your working directory.
2. **Stage Changes**: Use `git add` to move changes to the staging area.
3. **Commit**: Use `git commit` to save the staged changes in your Git directory.

---

## Tracking New Files, Modifying Files, and Viewing File Status  

### Tracking New Files  
When you add a new file to your project, Git does not track it automatically. You must explicitly tell Git to start tracking the file.  

1. **Add a New File**:  
   Create a new file in your working directory, for example:  
   ```bash
   echo "Hello, Git!" > newfile.txt
   ```  

2. **Stage the File**:  
   Use `git add` to stage the file:  
   ```bash
   git add newfile.txt
   ```  

3. **Commit the File**:  
   Commit the change to record it in the repository:  
   ```bash
   git commit -m "Add newfile.txt"
   ```  

### Modifying Files  
When you modify a tracked file, Git detects the change. To save this modification:  

1. Check the file’s status:  
   ```bash
   git status
   ```  
   The output will show the file as modified.  

2. Stage the changes:  
   ```bash
   git add modifiedfile.txt
   ```  

3. Commit the changes:  
   ```bash
   git commit -m "Update modifiedfile.txt"
   ```  

### Viewing File Status  
The `git status` command provides an overview of your working directory and staging area:  
- **Untracked Files**: Files not yet tracked by Git.  
- **Modified Files**: Files that have been changed but not yet staged.  
- **Staged Files**: Files that are ready to be committed.  

Example:  
```bash
git status
```  

---

## Making Commits  

A **commit** is a snapshot of the changes staged in your repository. It includes metadata such as the author, date, and a message describing the changes.  

### Committing Changes  
1. Stage the files you want to include in the commit:  
   ```bash
   git add <file-name>
   ```  

2. Commit the staged changes:  
   ```bash
   git commit -m "Your commit message"
   ```  

### Writing Meaningful Commit Messages  
Good commit messages improve collaboration and help you understand the history of a project. A standard commit message:  
- Is concise but descriptive.  
- Uses imperative mood (e.g., "Add feature," "Fix bug").  
- Clearly explains why the change was made, if necessary.  

Example:  
```bash
git commit -m "Fix login issue by updating authentication logic"
```  

### Inspecting Changes Before Committing
- Use `git diff` to view unstaged changes:  
  ```bash
  git diff
  ```
- View changes staged for commit:  
  ```bash
  git diff --staged
  ```

### Skipping the Staging Area
- Use `git commit -a` to automatically stage and commit changes to tracked files in one step:
  ```bash
  git commit -a -m "Message"
  ```

## Removing, Moving, and Renaming Files

### Removing Files
If you need to delete a tracked file from your repository and the working directory, use:
```bash
git rm <file>
```
This stages the removal for the next commit. To only remove the file from version control but keep it locally, add the `--cached` option:
```bash
git rm --cached <file>
```

### Moving and Renaming Files
Git tracks file movements and renames automatically if detected. However, you can explicitly move or rename files with:
```bash
git mv <old-file> <new-file>
```
This command:
1. Moves or renames the file.
2. Stages the change for the next commit.

If you manually move or rename a file outside Git, remember to stage the changes:
```bash
git add <new-file>
git rm <old-file>
```
